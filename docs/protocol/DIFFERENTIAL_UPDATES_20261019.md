# Windows differential installer distribution

The complete NSIS executable remains the release artifact and its existing SHA-256 is authoritative. A gzip electron-builder v2 blockmap is optional. Old clients continue downloading the complete executable; old releases without maps return 404 for the sidecar.

- `PUT /api/v1/admin/releases/:id/blockmap`: existing administrator authentication and CSRF rules; `application/octet-stream`; at most 2 MiB compressed and 16 MiB expanded. Requires a Windows x64 release and an existing installer. A published legacy release without a sidecar permits one audited first attachment; any existing published sidecar returns 409 and cannot be overwritten. Validates v2 checksum/size arrays and continuous coverage of every installer byte. Writes `<id>.exe.blockmap` atomically and audits the upload. Published sidecars cannot be changed. Upload holds the release row lock across validation and atomic file creation, serializing publication and concurrent backfills. Upload the installer, upload and verify its sidecar, then publish using the existing release PATCH. No database migration.
- `GET /api/v1/releases/files/:id/blockmap`: only published Windows x64 releases; optional sidecar absent => 404. Returns gzip bytes as `application/octet-stream` (without `Content-Encoding`, to prevent transparent decompression). The client must bound decompression and validate coverage too. Map blocks assist reconstruction, but never replace complete executable SHA-256 validation.
- `GET /api/v1/releases/files/:id`: unchanged complete 200 response when Range is absent. Strong ETag is the quoted executable SHA-256 and `Accept-Ranges: bytes` is advertised. One inclusive, open-ended, or suffix byte range returns 206 with exact Content-Range/Length. Invalid, unsatisfiable, or multiple ranges return 416 with `bytes */size`. If-Range must exactly match the strong ETag; a mismatch, weak ETag, or date falls back to full 200. Clients expecting a range must reject 200 as a range and perform their complete-download fallback.
- `GET /api/v1/releases/by-version/:version`: `{release}` for a published stable Windows x64 semantic version, otherwise 404. Enables a client that inherited an installer from an old updater to verify its current-version cache and obtain its map. The client must match version and hash before using that cache.

Publishing retains the three newest stable Windows x64 release records, installers, and sidecars. Older managed installers and sidecars are pruned together; official-client assets remain untouched. This bounded window requires roughly three complete installers on server disk (about 1 GB at current package size). Clients must retain their own verified current installer and blockmap, and fall back to full download whenever bootstrap metadata, the baseline, or a map is unavailable. No promise of indefinite historical downloads.

Downloads served as multiple 206 requests are not counted as separate full installer downloads by the existing site counter. End-to-end update completion telemetry is outside this change.

Validation: isolated-file Fastify injection with mocked database/authentication covers exact full/range responses, validators, rejection, sidecar publication visibility and authorization. These tests do not prove production proxy Range behavior, real administrator sessions, PostgreSQL concurrency, or an end-to-end installed update; those require deployment acceptance.
