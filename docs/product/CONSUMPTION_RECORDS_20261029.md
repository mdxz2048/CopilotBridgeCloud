# Device-first consumption records — local candidate

App 0.3.32 presents 消费记录 as device overview → device calls → charge explanation, following the approved local design. Today and seven-calendar-day filters use Asia/Shanghai midnight. Amounts are integer ledger points (10,000 = CNY 1) displayed to four decimal places.

Domain 2.11.0 adds signed, owner-scoped GET `/api/v1/me/consumption?range=today|week&deviceId=<internal device UUID>&page=1` and GET `/api/v1/me/consumption/{id}`. Each page has 20 rows. The overview includes all devices with records in the selected window. Responses use `Cache-Control: no-store`. Detail IDs can be usage-event UUIDs or `history:<device UUID>`. Browser sessions and device-bound desktop authentication follow the existing actor middleware. Other users' devices and records return 404. Only explicit usage and saved user-rate fields are returned; provider costs, request bodies, upstream payloads, audits and response IDs remain private.

Usage events supply actual charged points immediately, including open device intervals. Interval aggregation never creates another debit. Lifetime device interval totals plus open-counter deltas are reconciled against lifetime usage-event charges in one SQL snapshot. Only a positive unmatched remainder becomes one historical summary. Timestamp overlap cannot safely assign concurrent heartbeat/settlement transactions to periods, so historical residuals are deliberately not reconstructed as individual calls. Their filter timestamp is the latest recorded aggregation time, and their actual consumption may be earlier. UI explains this limitation.

METERING_ERROR/UNRATED amounts are null, never zero. UNPAID retains its actual partial debit, plus a separate rated amount in detail. Known partial debits count toward actual charged totals; unknown amounts do not. Zero-charge records remain explicitly zero. Cached input is part of total input; reasoning is part of total output. Standard immutable rate cards explain their respective categories and units. Provider-specific adjustments cannot be explained by a base card alone; rates and portions are withheld in that case. Two monetary portions are returned only when both are exact integer point amounts and sum to the actual SETTLED debit, with no image/tool charges, rounding difference or minimum-charge increment.

The compatible `/api/v1/me/bills` endpoint and settlement code are unchanged. Runtime desktop handshake remains 2.3.0 and minimum compatible App remains 0.3.28. No migration is needed for these reads. 0.3.32 is installed only as the separate local Preview product. Local seed data is synthetic, guarded to the loopback preview database and has no upstream credentials. No remote deployment, upload or Git push is authorized for this candidate.

Validation: API typecheck/build, 210 unit tests, 10 isolated PostgreSQL billing/consumption tests, 10 contract tests; App build/typecheck and 301 tests. Actual installed renderer and package verification are recorded separately after installation. DB tests run in disposable local `bridge_v2_test_consumption_20261029`, never in the persistent preview database. Existing production App and official client configuration must remain unchanged.
