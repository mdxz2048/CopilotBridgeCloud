# Bridge 连接、登录与闲鱼订单审核方案

设计稿：`purchase-review-design-20261017.html`，使用用户最新提供的闲鱼个人主页二维码。原型包含 App、网页、管理员、连接与登录四个视图，所有账号、余额、审核操作均为演示数据，不连接生产服务。

## 已确定的业务规则

2026-10-18 补充：充值全流程不提供“在闲鱼发消息”“联系卖家/管理员”“发送账号”等引导。管理员自行到闲鱼核实付款，用户仅扫码下单和提交订单号。

- 闲鱼服务名称：远程学习。
- 商品面额：10 元、20 元、50 元，用户按需下单。
- 按订单实际支付金额 1:1 发放人民币余额，实付 10 元到账 10 元，不额外兑换点数。
- 用户在 Bridge 中提交购买订单号；管理员应在提交后 10 分钟内审核。
- 当前采用人工核对，不假设拥有闲鱼订单查询 API。提交号码不代表已经验款，二维码也不作为付款凭据。
- 既有邀请奖励若满足活动规则，单独记奖励流水，不混入购买本金；本次不改变已有活动规则。

## 用户端：账号 → 充值

App 和网页共用同一服务端订单与状态。两端原有“联系管理员充值 / 加管理员微信”界面与旧二维码入口全部取消，统一替换为本方案，不并列保留第二种充值流程。

1. 左侧购买卡展示商品名称、三个面额、个人主页二维码、1:1 规则。文案：“用闲鱼扫码进入个人主页，选择‘远程学习’商品下单。”用户自行在个人主页找到对应商品并付款。
2. 二维码下方提供主按钮“已支付，提交订单号”。点击后弹出专属“手机提交订单”二维码，支持取消 / 关闭；不提前展开表单，不要求添加管理员、联系微信或向闲鱼卖家发送消息。
3. 手机扫码打开网页，无需再次登录，只输入完整购买订单号，不填金额。网页使用短期凭证绑定 App 当前账号，只展示掩码邮箱，不能填写或修改用户 ID / 邮箱。订单号按文本存储，不转数值、不丢前导零；格式限制根据真实订单样本确定，首尾去空格、最长 64 字符。
4. 提交成功显示：订单号、提交时间、待审核、10 分钟截止时间。允许关闭页面；再次打开从服务端恢复记录，不重置计时。
5. 审核通过显示“余额已到账 +¥10.00”，账户余额及账单同步刷新。未通过显示原因，用户核对订单号、按审核原因修改后可重新送审；不引导用户发闲鱼消息。
6. 超时仍显示待审核，并说明已超过 10 分钟、系统提醒管理员，用户可稍后刷新查看；不自动到账、不自动取消，不允许通过重复提交重置首次提交时间。
7. 提交列表切换“全部 / 待审核 / 已到账 / 未通过”，展示订单号、提交及处理时间、审核原因和到账金额。账单中显示“闲鱼订单到账”，可关联本人的订单详情。

提交结果超时不立即显示“失败”：显示“正在确认提交结果”，按幂等键查询是否已创建；用户可手动查询，同一订单不会重复创建。查询也失败则明确提示结果待确认，保留订单号。

## 手机专属提交链接（2026-10-18 更新）

- 保留两张用途不同的二维码：购买二维码进入闲鱼个人主页；点击“已付款”后生成的专属二维码打开本站手机订单页。
- App 必须已登录，服务端基于当前合法会话创建短期 ticket，绑定 userId、发起设备 / 会话及用途 `PURCHASE_CLAIM_SUBMIT`。不接受客户端传入任意 userId；不把裸 userId 当作授权凭据。
- 链接使用至少 256 位随机凭证，有效期建议 10 分钟，服务端仅存摘要。凭证放 URL fragment，手机 JS 通过 POST 换取仅限订单提交的短期 HttpOnly/Secure Cookie，并清除 fragment；避免 token 出现在反向代理 URL 日志、Referer、分析脚本或截图文字中。
- 绑定凭证只确定登记订单的 Bridge 账号，不代表系统已验证闲鱼付款归属；仍需管理员核实真实付款、金额及未兑付状态。
- 网页端若本身就在手机上操作，可在当前手机直接打开已绑定的提交页，避免要求用户扫描自己屏幕；电脑版网站与 App 保留二维码入口。
- 手机页不需要完整账号登录，不提供账户余额、资料、历史订单或设备权限；即使手机浏览器已登录另一个 Bridge 账号，也不改变专属提交页的到账对象。
- 页面展示掩码邮箱，用于用户辨认；不是自己的账号则关闭页面，回正确账号的 App 重新生成。凭证过期 / 撤销显示明确失效页，禁止继续提交。
- 同一 ticket 仅能成功登记一笔订单；重复点提交返回同一结果。提交不代表验款或到账，仍受全平台订单号唯一约束及管理员审核。
- 重新生成时旧 ticket 失效；源设备被移除、退出登录或账号被锁定时，未使用的 ticket 失效。移动提交服务做短期会话、速率及幂等校验。
- 手机提交完成后显示“已提交，等待审核”；App 仅在二维码窗可见时轻量查询 ticket 是否已使用，随后展示该订单状态。客户端断网可恢复，不靠手机直接写 App 状态。
- 专属链接有效期与审核时限分开：先在链接有效期内提交；提交成功后，从服务端记录的提交时间起计算管理员审核的 10 分钟。
- 手机页及订单过期、拒绝、待审等文案均不引导发闲鱼消息或联系卖家，管理员自行核对闲鱼订单。
- 当前原型二维码为设计示意，尚无线上 ticket 服务。可点击“预览手机页面”验证交互，不能把示意码当成已上线的扫码链接。

## 管理员端：订单审核

后台独立入口，显示待审核数量角标。沿用固定左侧导航，列表及详情在内容区滚动。

- 顶部：待审核、已超时、今日到账金额。默认待审核，按审核截止时间从早到晚排序；超时置顶。
- 列表：用户、平台、订单号、提交时间、截止时间 / 已超时、状态、审核入口。
- 详情：订单号、提交账号、实付金额、系统计算的同额到账金额、审核备注、历史处理记录。
- 管理员自行到闲鱼卖家后台核对实际付款状态、实付金额、订单归属及是否退款 / 关闭。填写“已核实实付金额”，系统按 1:1 自动算到账金额，不再单独手输到账金额。
- 通过前勾选核对确认；确认弹窗再次展示账号、订单号和到账金额。未通过必须填写用户可理解的原因。
- 已处理订单不能再次通过；两位管理员同时审核只允许一位成功，另一位收到“该订单已处理”并刷新当前行，不刷新整个后台页面。
- 待审核订单超过 10 分钟标记超时并增加后台提醒。需要系统通知时复用后台现有通知能力；短信、微信或邮件外发不默认启用。
- 不承诺用程序替代人工审核的 10 分钟响应：系统可以计时、排队和提醒，管理员仍需实际值守。

## 状态和资金一致性

状态流：待审核 → 已到账，或待审核 → 未通过；本人补充后允许未通过 → 待审核，并保留每轮历史及首次提交时间。超时是计算得到的标签，不是资金状态。

- 全平台按“平台 + 标准化订单号”唯一，跨账号也不能重复认领。本人重复提交返回已有记录；跨账号只提示该订单已提交，不泄露他人的账号。
- 管理员通过必须在同一个数据库事务内完成：锁定申请与钱包 → 校验仍待审核 → 按审核金额入账 → 写唯一钱包流水 → 更新审核状态、审核人和时间 → 写审计记录。
- 幂等键绑定申请 ID；请求超时、双击、重试、两位管理员并发均不重复发钱。
- 已到账记录不可直接修改金额或删除。审核错误或后续退款需要独立冲正流水及人工处理，保留原始凭证和审计；本次不自动连接闲鱼退款。
- 服务端计算金额，以整数最小单位存储；钱包沿用现有 1 元 = 10000 单位，转换时禁止浮点累计与溢出。前端显示人民币。
- 用户只能查看自己的申请；审核需要管理员权限，提交仅绑定当前登录用户。二维码及商品名称由管理配置控制，商品链接只有配置并验证后才展示打开按钮。

现有 billing_orders 强绑定套餐，不直接塞入新业务；新增 purchase_claims 和审核历史记录，复用现有钱包入账、批次、账单、审计与首次充值奖励规则，避免维护第二套余额。

## 未登录与失效会话

“未登录不能使用”作用于平台 Cloud 服务，不改动用户原账号的登录体系。

- 未登录或登录失效：模型选择、启用 Cloud、通过 Cloud 打开 / 重启、模型请求、提交订单均需先登录。界面显示明确登录入口，服务端和本地代理同时校验，不能只置灰按钮。
- 原账号恢复、注册、登录、找回密码、安装更新仍可用，避免用户被锁在失效的 Cloud 模式。
- access token 过期但可续期：所有并发请求合并为一次静默刷新，成功后原请求最多重试一次。
- refresh token 被拒绝、账号锁定、设备被撤销：按对应原因停止 Cloud 新请求、模型轮询、自动重连；明确要求重新登录或联系管理员。不得保留“已连接”假象，也不自动帮用户重新登录。
- 网络超时不等于登录失效，保留本地账号凭据。429 尊重 Retry-After，并退避；无有效会话时不继续每 5 秒打刷新接口。成功重新登录才恢复相应轮询。
- 登出与账号切换清理相关缓存，取消或隔离旧请求结果，防止旧账号结果回写到新账号界面。

## 超时机制建议

以下为拟实施预算，不代表当前程序已具备这些设置。

| 操作 | 建议预算 | 到期行为 |
| --- | --- | --- |
| 登录、静默续期 | 15 秒总时限 | 停止等待并提示；失效与网络失败分别处理 |
| 账号、余额、设备、模型列表 | 10 秒 | 取消请求，结束加载，可手动重试 |
| 本地连接启动 | 15 秒 | 返回连接失败，取消本次未完成启动，避免稍后偷偷恢复 |
| 提交订单 / 管理员审核 | 15 秒等待 | 不盲目重放写请求，先查幂等结果；未查明前显示结果待确认 |
| 打开外部链接 / 官方客户端 | 系统调用 10 秒，进程检测 15 秒 | 结束界面加载并给出重试说明；已经打开的外部程序不假装能撤回 |
| 模型上游连接 / 首个有效事件 | 建连 15 秒、首事件 120 秒 | 返回明确连接 / 首响应超时，取消上游请求 |
| 模型持续运行 | 沿用现有无进展和总时限，允许取消 | 正常持续输出不套用普通查询的 10 秒时限；保留长任务能力 |
| 更新下载 | 建连 15 秒、无数据 60 秒 | 清理不完整文件，可重试并重新校验；不能显示无限等待 |

所有异步按钮在成功、失败、超时、取消后恢复可操作；请求需要真正 Abort 或隔离迟到结果，不能只改提示文字。超时日志记录阶段、耗时和请求 ID，不记令牌、订单私密聊天或文档正文。

已有模型链路已包含分段时限，本次应核对 App、本地代理、Cloud、反向代理的一致性，优先补齐连接、登录与页面等待，不能全链路一刀切成 10 秒。

待审核状态只在页面可见时轻量查询，建议 30 秒一次、网络失败逐步延长，离开页面即暂停、进入终态即停止；余额复用已有同步，不新增全局 5 秒轮询。订单详情计时用服务端截止时间，前端每秒更新文字不请求服务器。

## 开发与验收顺序

1. 补登录有效性、刷新失败后的停止逻辑和超时取消，复现并消除 401/429 循环。
2. 新建申请、审核历史与唯一约束，隔离数据库测试并发审核、重复订单、超时结果查询、邀请奖励只发一次及资金事务回滚。
3. 实现管理员审核与 App / 网页充值入口，替换 App CloudAccountSheet 的旧 topup 视图与网页 TopupDialog，移除该充值流程对 admin-wechat.png 的引用，覆盖未登录、未填订单号、待审核、超时、未通过、已到账和跨账号拒绝。
4. 浅色 / 深色、窄窗口、复制、网络超时、重复点击、重启恢复状态验收；不通过真实用户订单或真实转账做自动测试。
5. 开发完成后按现有流程打包、部署、校验下载、记录版本并 Git 备份。本轮仅设计，未改生产业务代码、未部署，也未发布新 App。
